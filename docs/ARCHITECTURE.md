# Architecture and rationale

## Shape

SnakeCare AI uses a modular monolith first, with Clean Architecture inside each bounded module:

```text
Interface (FastAPI / Flutter UI)
          ↓
Application (use cases, ports)
          ↓
Domain (entities, rules)
          ↑
Infrastructure (PostgreSQL, Redis, Firebase, external providers)
```

The backend is versioned under `/api/v1`. Modules own their domain, application, infrastructure, presentation, and tests. Cross-cutting configuration, observability, error handling, and database lifecycle live in `core`. The Flutter app mirrors feature-first Clean Architecture with `presentation`, `domain`, and `data` layers plus a small shared core.

Module 7 adds a `hospital_dashboard` vertical slice. It owns reviewed facility claims, hospital inbox decisions, hospital-reported resource publication, antivenom box records, pending depletion approvals, and hospital audit events. It consumes Module 6 facility and availability records but does not change the patient recommendation engine's ownership boundary.

Ambulance dispatch remains outside the SnakeCare boundary. Module 8 adds a safety-gated, simulation-only 112 handoff: it prepares a consented, source-labelled snapshot, rehearses allow-listed operator questions, and can open the device dialler for a human-controlled call. It has no ERSS, PSTN, SIP, dispatch, fleet, or live-tracking adapter. The retired ambulance migration remains in history so existing installations and audit data are not damaged.

## Why this design

A modular monolith is fast to operate for a hackathon and early startup while enforcing seams that can later become services. Dependency inversion protects clinical rules from FastAPI, Firebase, Gemini, maps, and storage vendors. PostgreSQL provides transactional integrity and auditable migrations; Redis is optional and must never be a system of record. Async I/O supports live emergency workloads without forcing premature distribution.

## Quality and safety boundaries

- Every generated clinical artifact will later carry source references, confidence, missing-data markers, model metadata, and a generated/verified status.
- Logs contain correlation IDs and operational metadata, never raw protected health information.
- Authentication and authorization arrive in Module 2; no protected domain endpoint is exposed in Module 1.
- External providers will be ports/adapters so Gemini, Firebase, OSRM, OCR, and storage can be replaced.
- Future emergency types share a general emergency-case core and add condition-specific modules.

## Initial database foundation

Module 1 creates only `system_metadata`, proving migrations, UUID keys, timezone-aware timestamps, and JSONB support. Domain tables from the master plan are intentionally deferred to their owning modules to avoid speculative coupling. Naming rules: plural snake_case tables, UUID primary keys, UTC timestamps, explicit foreign keys, indexed lookup fields, and additive/reversible migrations. Sensitive fields will use application/envelope encryption and least-privilege roles when introduced.

## Initial API foundation

| Method | Path | Purpose | Database required |
|---|---|---|---|
| GET | `/api/v1/health` | Process liveness | No |
| GET | `/api/v1/ready` | PostgreSQL readiness | Yes |

Responses use a typed envelope for status information. Errors use RFC 9457-style `application/problem+json` payloads with a request ID. OpenAPI is generated by FastAPI. Later modules add resources without changing these operational contracts.

## Deployment topology

The API runs as a non-root container behind TLS termination. PostgreSQL is the source of truth; Redis is optional. Migrations run as a release job before application rollout. Mobile configuration is injected with Dart defines, while Firebase native configuration is generated per environment via FlutterFire and excluded from Git. Production should use managed databases, secret management, encrypted backups, health probes, centralized logs, metrics/traces, and separate dev/staging/prod projects.
